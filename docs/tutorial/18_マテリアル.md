# 18. マテリアル

[15 章](15_モデルを読み込む_OBJ.md)・[16 章](16_モデルを読み込む_glTF.md)で
モデルを読めるようになり、[17 章](17_画像を読み込む_WIC.md)で画像も読めるようになりました。

しかし、**ファイルに書かれた色や質感は捨てていました**。
モデル全体が 1 色、テクスチャも全体で 1 枚だけです。

この章で、その 2 つをつなぎます。

![材質ごとに色とテクスチャが変わったシーン](../assets/materials-scene.png)

対応するコードは [`src/Graphics/MaterialSet.h`](../../src/Graphics/MaterialSet.h)、
[`GltfLoader.cpp`](../../src/Assets/GltfLoader.cpp)、
[`ObjLoader.cpp`](../../src/Assets/ObjLoader.cpp) です。

## 1. 1 つのメッシュに複数の材質

これまでの前提は「1 メッシュ ＝ 1 回の `DrawIndexedInstanced`」でした。
材質が複数あると、この前提が崩れます。

**材質が変わるたびに描画を区切る**必要があるからです。
テクスチャや定数バッファは、描画命令の途中では差し替えられません。

そこで、インデックスの並びを材質ごとの範囲に分けます。

```cpp
struct SubMesh
{
    uint32_t indexOffset;    // インデックス配列の何番目から
    uint32_t indexCount;     // 何個ぶん
    uint32_t materialIndex;  // どの材質で
};
```

これを**サブメッシュ**と呼びます。

### 描画は入れ子のループになる

```cpp
m_meshPipeline.Bind(cmdList, frameIndex, shadowView);          // 1 フレームに 1 回

for (オブジェクト)
{
    m_meshPipeline.BindObject(cmdList, frameIndex, objectIndex);   // 変換行列

    for (サブメッシュ)
    {
        m_meshPipeline.BindMaterial(cmdList, 定数, テクスチャ);      // 色とテクスチャ
        mesh.RecordDrawCommands(cmdList, indexOffset, indexCount);
    }
}
```

外側から内側へ、**書き換わる頻度の順**に並んでいます。
[12 章](12_複数のモデルを描く.md)で定数バッファを頻度で分けたのと同じ考え方です。

### 描く範囲だけを変える

```cpp
commandList->DrawIndexedInstanced(indexCount, 1, indexOffset, 0, 0);
```

第 3 引数が「何番目のインデックスから始めるか」です。
**頂点バッファもインデックスバッファも設定し直しません。**
同じバッファのまま、描く範囲だけを変えられます。

## 2. テクスチャの有無で分岐しない

材質にはテクスチャがあるものと無いものが混ざります。
素直に書くとシェーダーに分岐が入ります。

```hlsl
// こうはしない
float4 color = g_hasTexture ? g_texture.Sample(...) : float4(1,1,1,1);
```

代わりに、**テクスチャを持たない材質には白 1 ピクセルの画像を割り当て**ます。

```cpp
assets::ImageData CreateWhitePixel()
{
    ImageData image;
    image.width  = 1;
    image.height = 1;
    image.pixels = { 255, 255, 255, 255 };
    return image;
}
```

白を掛けても色は変わらないので、基本色がそのまま出ます。
シェーダーは常に同じ 1 本の道を通ります。

> 分岐そのものが遅いというより、**分岐が無いほうが読みやすく、間違いが減る**のが利点です。
> 1×1 の画像はメモリもほとんど食いません。
> テクスチャを持たない材質が何個あっても、この 1 枚を共有します。

## 3. glTF のマテリアル

glTF は PBR（物理ベースレンダリング）を前提にした構造です。
本プロジェクトが読むのは、そのうち**基本色だけ**です。

```json
"materials": [{
  "name": "HeadBanded",
  "pbrMetallicRoughness": {
    "baseColorFactor": [1.0, 1.0, 1.0, 1.0],
    "baseColorTexture": { "index": 0 }
  }
}]
```

| 項目 | 意味 |
|------|------|
| `baseColorFactor` | 基本色 (r, g, b, a)。テクスチャと掛け合わせる |
| `baseColorTexture` | 基本色テクスチャ。`textures` の番号 |

金属度・粗さ・法線マップ・発光は読み飛ばしています。
本プロジェクトのシェーダーが対応していないためです。

### 画像へたどり着くまで

```
materials → textures → images → （bufferView / data URI / 外部ファイル）
```

[16 章](16_モデルを読み込む_glTF.md)の buffers と同じく、
**画像の置き場所も 3 通り**あります。

同梱の `scene.glb` は、PNG を**ファイル内に埋め込んで**います
（`images[0].bufferView`）。GLB のバイナリチャンクの中に
PNG のバイト列がそのまま入っている形です。

```cpp
// PNG / JPEG のバイト列がそのまま入っている。デコードは WIC に任せる。
return assets::DecodeImageBytes(bytes.data() + offset, length);
```

[17 章](17_画像を読み込む_WIC.md)で用意した `DecodeImageBytes` が、
ここで初めて役に立ちます。

### プリミティブが材質を指す

```json
"primitives": [{ "attributes": {...}, "indices": 3, "material": 1 }]
```

**プリミティブ 1 個 ＝ サブメッシュ 1 個**です。
glTF の構造がそのままサブメッシュの区切りになるので、素直に対応が取れます。

## 4. OBJ のマテリアル（.mtl）

OBJ は色を別ファイルに置きます。

```
mtllib pyramid.mtl     ← 材質の定義ファイルを読み込む
...
usemtl Sides           ← ここから先の面は Sides で描く
f 1/1 2/2 5/3
usemtl Bottom          ← ここから先は Bottom
f 1/1 4/5 3/4 2/2
```

`.mtl` の中身はこうです。

```
newmtl Sides
Kd 0.86 0.72 0.42          ← 拡散色
map_Kd ../textures/uv-grid.png   ← 拡散テクスチャ
```

| 行 | 意味 |
|----|------|
| `newmtl 名前` | 新しい材質を始める |
| `Kd r g b` | 拡散色（基本色に相当） |
| `map_Kd パス` | 拡散テクスチャ |

鏡面色 `Ks`、透明度 `d`、輝度 `Ns` などは読み飛ばしています。

### usemtl で区切る

glTF と違い、OBJ は**面の並びの途中で材質が切り替わり**ます。
そのため、`usemtl` が来るたびに「ここまでのサブメッシュ」を閉じます。

```cpp
const auto closeSubMesh = [&]() {
    const uint32_t here = static_cast<uint32_t>(mesh.indices.size());
    if (currentMaterial != UINT32_MAX && here > currentStart)
    {
        // …サブメッシュを 1 つ追加
    }
    currentStart = here;
};
```

**ファイルの最後でも閉じる**のを忘れないでください。
最後の `usemtl` 以降の面が丸ごと消えます。

### map_Kd のパスは空白を含みうる

```cpp
std::string name;
std::getline(stream, name);   // 行の残り全部
```

`>>` で読むと空白で切れてしまいます。
`Program Files` のようなフォルダ名を含むパスで壊れる、
という形で表面化します。

## 5. 読み込み側と描画側の橋渡し

読み込み結果はただのデータです。GPU 上の資源にするのが `MaterialSet` です。

| 材質が持つもの | GPU 上での姿 |
|--------------|------------|
| 基本色 | 定数バッファの 1 スロット |
| テクスチャ | `Texture2D` と SRV |

```cpp
class MaterialSet
{
    std::vector<std::unique_ptr<Texture2D>> m_textures;
    std::vector<uint32_t> m_textureIndices;   // 材質 → テクスチャ
    ConstantBuffer m_constants;               // 材質の数ぶんのスロット
};
```

### フレーム別に分けなくてよい

[12 章](12_複数のモデルを描く.md)では
「オブジェクト別の定数はフレーム数 × オブジェクト数ぶん要る」と書きました。

材質の定数は**フレーム別に分ける必要がありません**。
読み込んだ後は一度も書き換わらないからです。
GPU が前のフレームを読んでいる最中に上書きする、という事故が起きません。

「フレーム別に分けるのは**書き換えるから**」であって、
「定数バッファだから」ではない、という区別です。

### MeshPipeline はテクスチャを持たなくなった

これまで `MeshPipeline` が唯一のテクスチャを抱えていましたが、
材質ごとに違うものになったので手放しました。

```cpp
void BindMaterial(commandList, constantAddress, textureView) const;
```

差し替えるのは**定数バッファ 1 本とディスクリプタテーブル 1 つ**だけです。
[12 章](12_複数のモデルを描く.md)の表のとおり、PSO の切り替えより遥かに軽い処理です。

## 6. 影のパスは材質を見ない

```cpp
// 影の形しか要らないので、材質で区切らずメッシュ全体を一度に描く。
m_model.RecordDrawCommands(commandList);
```

[13 章](13_影を落とす_シャドウマップ.md)のシャドウマップは深度だけを書きます。
色もテクスチャも使わないので、**サブメッシュに分ける意味がありません**。

区切らないぶん描画命令が減るので、速さの面でも素直です。

> 半透明や、テクスチャのアルファで穴を開ける材質を扱うようになると、
> 影のパスでもテクスチャが要ります。そのときは分ける必要が出てきます。

## 7. 測って確かめる

### 数が合うか

`scene.glb` は 3 つの材質を持つよう生成しました。

| 項目 | 生成時の値 | 読み込み結果 |
|------|----------|------------|
| プリミティブ | 3 | 3 |
| サブメッシュ | 3 | 3 |
| 頂点 | 612 | 612 |
| 三角形 | 1052 | 1052 |
| 材質 | 3 | **4**（＋既定の 1 つ） |
| テクスチャを持つ材質 | 1 | 1 |

材質が 1 つ多いのは、**材質を持たないファイルでも描けるように**
白 1 色の既定を末尾に足しているためです。

### 色が正確に届いているか

箱の材質 `BaseTeal` は `baseColorFactor = (0.25, 0.62, 0.60)`、テクスチャ無しです。

光の当たっていない面は環境光（0.25）だけになるので、
画面に出るはずの色は次のように計算できます。

```
0.25 × 0.25 × 255 = 15.9
0.62 × 0.25 × 255 = 39.5
0.60 × 0.25 × 255 = 38.3
```

実測は **(16, 39, 38)**。式に当てはめて拡散・鏡面を逆算したところ、
**3 チャンネルとも誤差 0 / 255** でした。

ファイルに書いた値が、途中で薄まったり掛け違ったりせず、
そのまま画面に届いていることが確認できます。

> 頂点カラーを**白に変えた**のがここで効いています。
> 以前は読み込み時に頂点へ色を書いていたので、
> 材質の色と掛け合わさって二重に暗くなっていました。
> 色は材質が持つ、と決めたことで計算が素直になっています。

## 8. この章のまとめ

- 材質が複数あると **1 メッシュ ＝ 1 回の描画**という前提が崩れる
- インデックスの範囲を**サブメッシュ**に分け、材質ごとに区切って描く
- `DrawIndexedInstanced` の第 3 引数で、描く範囲だけを変えられる
- 描画は「フレーム → オブジェクト → 材質」の入れ子。**書き換わる頻度の順**
- テクスチャの無い材質には**白 1 ピクセル**を割り当て、分岐を無くす
- glTF は `materials → textures → images`。画像も 3 通りの置き場所がある
- OBJ は `.mtl` に材質を置き、`usemtl` で切り替える。**最後に閉じ忘れない**
- `map_Kd` のパスは行末まで読む。空白を含みうる
- 材質の定数は**フレーム別に分けなくてよい**。書き換わらないから
- 影のパスは材質を見ない。深度しか書かないため

## 9. ここから先へ

| やりたいこと | 必要になるもの |
|------------|--------------|
| 金属や粗さを反映する | PBR のシェーディングモデル（`metallicRoughnessTexture`） |
| 表面の凹凸を出す | 法線マップと接空間（タンジェント） |
| 半透明を扱う | アルファブレンド、描画順の並べ替え |
| 描画を速くする | 材質ごとに並べ替え、同じ PSO をまとめる |
| 色を正しく扱う | sRGB のガンマ補正 |
